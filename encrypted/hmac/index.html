HMAC 结果

HMAC：带密钥的消息认证码

为什么需要 HMAC

  • 普通哈希（如 SHA-256）只能验证数据完整性，无法验证数据来源。攻击者可以在篡改数据后重新计算哈希。HMAC 通过引入共享密钥，同时实现完整性校验和身份认证。
  • 本工具支持 HMAC-SHA256/SHA384/SHA512 三种常用算法，提供生成和校验两种模式，输出可选 Hex 或 Base64，适用于 API 请求签名、Webhook 验证等场景。

核心功能

  • HMAC 生成：输入密钥和消息，一键生成消息认证码。
  • HMAC 校验：输入待校验的 HMAC，自动比对并提示是否匹配。
  • 双格式输出：支持 Hex 和 Base64 两种常见编码。
  • 本地处理：所有计算在浏览器中完成，密钥和消息不上传服务器。

使用指南

生成步骤

  • 选择算法：一般推荐 HMAC-SHA256，安全要求极高可选 SHA512。
  • 输入密钥：使用双方约定的共享密钥。
  • 输入消息：即需要签名的原始数据。
  • 点击生成：获得 Hex 或 Base64 格式的 HMAC。

校验步骤

  • 输入三要素：算法、密钥、消息必须与生成方完全一致。
  • 输入待校验 HMAC：工具会自动识别 Hex 或 Base64 格式。
  • 点击校验：显示匹配或不匹配结果。

安全建议

  • 密钥保密：HMAC 的安全性完全依赖密钥保密，不要明文传输。
  • 算法一致：生成和校验必须使用完全相同的算法、密钥和消息编码。

典型应用场景

典型应用场景

  • API 请求签名：客户端与服务端共享密钥，对请求方法、路径、时间戳和请求体拼接后的字符串计算 HMAC，将结果放在 Authorization 头中。服务端用相同密钥重新计算并比对，有效防止请求参数被篡改或重放攻击。
  • Webhook 验证：GitHub、Stripe、钉钉等平台在推送 Webhook 时会附带 HMAC-SHA256 签名。接收方提取请求体，用预先配置的密钥计算 HMAC，与请求头中的签名比对，确认事件确实来自该平台。
  • JWT 签名验证：JWT 的 HS256/HS384/HS512 签名模式本质就是 HMAC。本工具可用于调试 JWT 签名逻辑、验证 Token 是否由持有密钥的服务端签发。
  • 软件分发校验：在固件更新、安装包下载等场景中，发布者可以同时提供文件和 HMAC 值。用户下载后用相同密钥计算 HMAC，既可确认文件未被篡改，也能验证发布者身份。

技术优势

  • 算法标准：严格遵循 RFC 2104 和 Web Crypto API，计算结果与 Python hmac、Node.js crypto、Java javax.crypto 等主流库完全兼容。
  • 双模式支持：同时支持 HMAC 生成和校验，一站式满足签名与验证需求，无需在多个工具间切换。
  • 格式灵活：输出可选 Hex 或 Base64，便于与不同协议、数据库字段和日志系统对接。
  • 本地安全：所有计算在浏览器本地完成，密钥和消息不会上传到服务器，适合处理敏感数据。

算法选择建议

HMAC-SHA256 是目前最常用、兼容性最好的算法，适用于绝大多数 API 签名和 Webhook 验证场景。HMAC-SHA384 和 HMAC-SHA512 提供更高的安全冗余，计算开销也相应增加，适合金融、政务等对安全性要求极高的场景。

常见问题

  • Q: HMAC 和普通哈希有什么区别？A: HMAC 引入了密钥——只有持有密钥的人才能计算和验证 MAC 值。普通哈希任何人都能重新计算。HMAC 同时提供完整性校验和身份认证。
  • Q: HMAC 的密钥长度有要求吗？A: 没有严格限制，但建议密钥长度至少与哈希输出长度相同（如 HMAC-SHA256 建议至少 32 字节）。密钥过短时，可先用哈希函数派生。
  • Q: HMAC 能和 MD5 配合使用吗？A: 技术上可以，但 MD5 的碰撞漏洞会影响 HMAC 的安全性。建议搭配 SHA-256 或更高算法。
  • Q: HMAC 是加密吗？A: 不是。HMAC 是消息认证码，不提供数据保密性——它只验证消息完整性和来源。如需保密，先用 AES 加密数据，再用 HMAC 认证。
