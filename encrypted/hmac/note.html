什么是 HMAC？

HMAC（Hash-based Message Authentication Code，基于哈希的消息认证码）是一种结合加密哈希函数与共享密钥的消息认证机制，由 RFC 2104 定义。它通过让密钥参与哈希计算，既能检测消息在传输过程中是否被篡改，又能验证消息是否来自持有相同密钥的合法发送方。

与普通哈希算法不同，HMAC 不是简单的数据指纹。普通哈希（如 SHA-256）任何人都可以重新计算，因此无法防止伪造。而 HMAC 由于引入了只有通信双方知道的密钥，即使攻击者截获了消息，也无法在没有密钥的情况下生成合法的认证码。这一特性使 HMAC 成为 API 签名、Webhook 验证和 JWT 签名的核心算法。

本工具基于浏览器原生 Web Crypto API 实现，严格遵循 RFC 2104 标准，支持 HMAC-SHA256、HMAC-SHA384、HMAC-SHA512 三种主流算法，提供生成和校验两种模式，输出可选 Hex 或 Base64 编码。所有计算在浏览器本地完成，密钥和消息都不会上传到服务器。

HMAC 的工作原理

HMAC 的计算过程可以概括为：先用密钥与消息进行"内层"哈希，再用密钥与内层结果进行"外层"哈希。具体公式为：

HMAC(K, m) = H((K' ⊕ opad) || H((K' ⊕ ipad) || m))

其中，K 是原始密钥，K' 是填充或截断到哈希块大小的密钥，ipad 和 opad 是固定的填充常量，H 是哈希函数（如 SHA-256），m 是待认证消息。双层结构有效抵抗了针对哈希函数的扩展攻击和密钥恢复攻击。

四步完成 HMAC 生成与校验

第一步：选择算法

根据安全需求选择合适的哈希算法。HMAC-SHA256 是目前最常用、兼容性最好的选择；HMAC-SHA384 和 HMAC-SHA512 提供更高的安全冗余，适用于对安全性要求更高的场景。

第二步：输入密钥

密钥是 HMAC 安全性的核心。通信双方必须使用完全相同的共享密钥。密钥应足够随机且保密，建议长度至少 256 位（32 字节），避免使用简单字符或公开信息。

第三步：输入消息

消息即需要被认证的原始数据。在 API 签名的场景中，这通常是请求方法、路径、时间戳和请求体按约定顺序拼接后的字符串。消息的任何微小变化都会导致 HMAC 值完全不同。

第四步：生成或校验

点击生成按钮获得 HMAC 值，或输入待校验的 HMAC 进行比对。生成与校验必须使用相同的算法、密钥、消息和输出格式，任一差异都会导致校验失败。

算法选择建议

HMAC-SHA256

目前最广泛使用、兼容性最佳的算法。计算速度快，安全性强，适用于绝大多数 API 签名、Webhook 验证和 JWT 调试场景。

推荐用于大多数场景 兼容性好

HMAC-SHA384

提供比 SHA-256 更高的安全冗余，哈希输出为 384 位。适用于对安全性要求较高的金融、医疗和企业内部系统。

高安全性场景 计算开销适中

HMAC-SHA512

安全冗余最高，哈希输出为 512 位。适合对长期安全性和抗量子计算有更高要求的场景，但计算开销也最大。

最高安全等级 计算开销较大

典型应用场景

API 请求签名：服务端与客户端约定密钥，客户端对请求参数计算 HMAC 并附在请求头中，服务端用相同密钥校验，防止请求被篡改或重放。

Webhook 验证：GitHub、Stripe、钉钉等平台在推送 Webhook 时附带 HMAC 签名，接收方通过验证签名确认事件来源的真实性。

JWT 签名验证：JWT 的 HS256/HS384/HS512 签名模式本质就是 HMAC。本工具可用于调试和验证签名逻辑。

文件分发校验：在软件下载、固件更新等场景中，HMAC 可确保文件未被篡改并确认发布者身份。

技术优势

RFC 2104 标准 Web Crypto API HMAC-SHA256 HMAC-SHA384 HMAC-SHA512 生成与校验 Hex/Base64 输出 本地处理

注意事项：

  • 密钥必须保密，不要通过不安全渠道传输或保存在代码仓库中
  • 生成和校验必须使用完全相同的算法、密钥、消息编码和输出格式
  • HMAC 不能加密数据，仅用于完整性与来源认证
  • 本工具所有计算在浏览器本地完成，数据不上传服务器

实战案例：REST API 请求签名

某电商平台需要为开放 API 设计一套轻量级认证机制。平台为每个开发者分配一个 App Secret，开发者调用 API 时需要对请求生成 HMAC-SHA256 签名。

签名流程：

  1. 将 HTTP 方法、请求路径、时间戳和请求体按顺序拼接成待签名字符串，例如：GET|/api/v1/orders|1699123456|{}。
  2. 使用 App Secret 作为密钥，对待签名字符串计算 HMAC-SHA256，得到 64 字符的 Hex 字符串。
  3. 将签名放入请求头 Authorization: HMAC-SHA256 {signature}，同时发送时间戳。
  4. 服务端收到请求后，用相同密钥和相同拼接规则重新计算 HMAC，与请求头中的签名比对。若不一致则拒绝请求，防止参数篡改。

效果：该方案无需复杂的 OAuth 或证书体系，仅需一个共享密钥即可实现请求防篡改和来源验证，部署成本低且兼容性好。同时，时间戳的引入还能有效防御重放攻击。

安全最佳实践

  • 密钥生成：使用密码学安全随机数生成器生成密钥，长度至少 256 位。避免使用用户密码、用户名或固定字符串作为密钥。
  • 密钥存储：服务端应将密钥存储在密钥管理系统（KMS）或环境变量中，切勿硬编码在源代码或前端配置文件中。
  • 消息规范化：通信双方必须严格约定消息的拼接规则、编码方式和字段顺序。建议对空值、换行符和 Unicode 字符做明确约定。
  • 防止重放攻击：在消息中加入时间戳或随机数（nonce），服务端校验时间戳是否在合理窗口内，nonce 是否已被使用。
  • 定期轮换密钥：对于长期使用的 API 密钥，建议定期轮换，并支持旧密钥的平滑过渡。
  • 区分 HMAC 与加密：HMAC 不能保护数据机密性，只能验证完整性和来源。敏感数据在传输前仍需使用 TLS 和 AES 等加密手段。

常见问题

问：HMAC 能加密数据吗？

答：不能。HMAC 只用于验证数据完整性和来源，不能隐藏数据内容。如需加密，请使用 AES 等对称加密工具。

问：校验失败是什么原因？

答：最常见原因是算法、密钥或消息不一致。也可能是因为输入的 HMAC 格式错误（Hex 或 Base64 混淆）、消息编码不同（如 UTF-8 与 GBK）或拼接顺序不一致。请逐项核对生成与校验时的所有参数。

问：HMAC-SHA256 比 SHA256 更安全吗？

答：两者解决的问题不同。SHA256 用于生成公开可验证的摘要，HMAC-SHA256 用于在双方共享密钥的前提下验证完整性和来源。只要密钥保密，HMAC 可提供更强的防伪造能力。

问：为什么 HMAC 需要双层哈希？

答：双层哈希结构（内层和外层）是 RFC 2104 的核心设计。它有效抵抗了针对哈希函数的扩展攻击（length extension attack）和部分密钥恢复攻击，确保即使底层哈希函数存在某些弱点，HMAC 仍能保持较高的安全性。

问：HMAC 输出应该选 Hex 还是 Base64？

答：Hex 格式易于阅读和调试，常用于日志和调试场景。Base64 格式更紧凑，长度约为 Hex 的三分之二，适合在 HTTP 头、URL 参数和 JSON 字段中传输。选择哪种格式取决于下游系统的约定。
