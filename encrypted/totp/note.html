什么是 TOTP？

TOTP（Time-based One-Time Password，基于时间的一次性密码）是一种由 IETF 在 RFC 6238 中定义的双因素认证（2FA）标准。它结合了共享密钥和当前时间，通过 HMAC 算法生成一个只在短时间内有效的动态口令。典型的 TOTP 口令每 30 秒更新一次，每次使用后即失效，因此即使攻击者截获了当前口令，也无法在下一个时间窗口内再次使用。

TOTP 的核心计算过程如下：首先将当前 Unix 时间戳按周期（通常为 30 秒）取整得到时间计数器；然后使用共享密钥对计数器计算 HMAC（常用 HMAC-SHA1）；最后从 HMAC 结果中按特定规则截取 6 位或 8 位十进制数字作为动态口令。由于通信双方持有相同的密钥且时间同步，因此能生成一致的口令。

本工具严格遵循 RFC 6238 / RFC 4226 标准，使用浏览器原生 Web Crypto API 执行 HMAC 计算。只要输入正确的 Base32 密钥并选择对应的算法、位数和周期，生成的口令就与 Google Authenticator、Microsoft Authenticator、Authy 等主流验证器完全一致。密钥仅在浏览器本地使用，不会上传到服务器。

三步生成动态口令

第一步：输入 Base32 密钥

从服务提供的二维码或文本中获取 Base32 编码的密钥，并粘贴到工具中。Base32 字符集仅包含 A-Z 和 2-7，密钥长度通常为 16、24 或 32 个字符。这个密钥与您的密码等效，务必妥善保管。

第二步：配置参数

大多数服务使用默认配置：SHA-1 + 6 位数字 + 30 秒周期，这也是 Google Authenticator 的默认设置。部分企业或高安全服务可能使用 SHA-256/SHA-512 和 8 位数字。请确保算法、位数、周期与服务端配置完全一致，任一参数不同都会导致口令不匹配。

第三步：生成并使用口令

点击生成按钮，工具会显示当前有效的动态口令，并通过倒计时条提示下次刷新时间。在口令过期前将其输入到登录界面的二次验证框中即可完成认证。

典型应用场景

账户二次验证（2FA）：为邮箱、网银、社交媒体、云服务、代码托管平台等开启 TOTP 二次验证。即使密码泄露，攻击者没有密钥也无法登录。

开发者调试：在实现 TOTP 登录流程时，使用本工具验证服务端生成的口令是否正确，排查密钥、算法、位数或周期配置问题。

临时替代验证器：当手机不在身边、验证器 App 损坏或更换设备时，可临时使用本工具获取口令完成登录。

安全测试与兼容验证：测试 TOTP 系统的跨平台兼容性，确保服务端与客户端使用完全相同的算法参数。

安全注意事项：

  • TOTP 密钥与密码等效，泄露后攻击者可生成相同口令
  • 切勿截图保存到云端、发送给他人或保存在不安全的代码仓库中
  • 设备时间必须准确（建议开启 NTP 网络时间同步），否则口令会与服务端不一致
  • 本工具仅用于临时生成口令或开发调试，不建议长期保存密钥在浏览器中
  • 所有计算在浏览器本地完成，密钥不上传服务器

常见问题

问：生成的口令和验证器不一致？

答：请检查密钥、算法、位数和周期是否与服务配置完全一致，同时确认本机时间准确。任何一个参数不同，或设备时间偏差超过几个周期，都会导致口令不一致。

问：本工具可以代替验证器 App 吗？

答：可以临时使用，但不建议长期保存密钥在浏览器中。专用验证器 App（如 Google Authenticator、Microsoft Authenticator、Authy）通常具有更好的安全隔离、备份和恢复机制。

问：TOTP 和短信验证码有什么区别？

答：TOTP 不依赖网络和短信通道，由设备本地基于密钥和时间生成，不受 SIM 卡交换攻击（SIM Swap）和短信拦截影响。而短信验证码可能被运营商、中间人攻击或钓鱼手段截获，安全性相对较低。

问：为什么需要二次验证？

答：据统计，超过 80% 的账户入侵源于密码泄露、钓鱼攻击或凭证填充。二次验证在密码之外增加了一道防线，即使密码被盗，攻击者通常也无法通过第二因素认证，从而大幅降低账户被盗风险。

安全最佳实践

  • 密钥保密：不要在代码仓库、前端配置或不安全渠道中泄露密钥或敏感凭证。
  • 本地优先：本工具所有计算在浏览器本地完成，处理完成后及时关闭页面，避免敏感信息驻留。
  • 结合多层防护：单一工具不足以构建完整安全体系，建议配合 TLS、访问控制、审计日志等措施。
  • 定期轮换：对长期使用的密钥、令牌或凭证建立轮换机制，降低泄露后的影响范围。
  • 选择合适算法：根据安全需求选择算法长度和模式，优先使用经过广泛验证的标准方案。

实战案例：接口请求安全加固

某团队在开放 API 时，需要为第三方调用者提供一种轻量且可靠的鉴权方式。通过 TOTP/OTP 生成器，服务端为每个开发者分配唯一凭证，并要求请求中附带基于该工具生成的签名或令牌。

实施流程：

  1. 开发者在控制台获取由 TOTP/OTP 生成器 生成的密钥或凭证。
  2. 调用 API 前，按照约定格式拼接请求参数与时间戳，使用 TOTP/OTP 生成器 计算签名。
  3. 将签名放入请求头，服务端使用相同逻辑重新计算并比对。
  4. 若签名一致且时间戳在有效窗口内，则放行请求；否则拒绝，防止重放和篡改。

效果：该方案无需复杂证书基础设施，仅通过浏览器本地即可完成计算，部署成本低且兼容性好。
