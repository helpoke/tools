二、Token 格式

  • JWT 结构：三段 Base64URL 编码用点号分隔——Header.Payload.Signature。Header 声明算法（如 HS256），Payload 包含声明（iss/sub/exp 等），Signature 用 Secret 对前两段签名。
  • 随机 Token：纯随机字符串——可自定义长度（8-256 位）、字符集（大写/小写/数字/符号）和格式（原始/UUID/Hex）。用于 API Key、Session ID、CSRF Token 等场景。

三、核心功能

  • JWT 解析：粘贴 JWT 自动解码——显示 Header（算法/类型）、Payload（所有声明，时间戳自动转为可读格式）、Signature（验证签名有效性）。
  • 随机 Token 生成：自定义长度、字符集和格式——一键生成安全的随机 Token。支持批量生成多个。
  • JWT 生成：设置 Secret、选择算法（HS256/HS384/HS512）、填写 Payload 声明——生成完整的签名 JWT。
  • 纯前端处理：所有解析和生成在浏览器中完成——Token 和 Secret 不上传到服务器。

JWT 解析指南

解析步骤

  • 粘贴 JWT：将完整的 JWT 字符串粘贴到输入框——以 eyJ 开头的三段式字符串。
  • 输入 Secret：输入签名密钥——用于验证 Signature 是否有效。不知道 Secret 也能解析 Header 和 Payload。
  • 点击解析：工具自动将 JWT 拆分为三段并解码。
  • Header 解析：显示 alg（签名算法，如 HS256）和 typ（类型，固定为 JWT）。
  • Payload 解析：显示所有声明——iss（签发者）、sub（主题）、exp（过期时间）、iat（签发时间）等。时间戳自动转为人类可读格式。
  • 时间验证：自动检查 exp（是否过期）和 nbf（是否生效）——显示当前时间与 Token 有效期的对比。
  • 签名验证：用 Secret 重新计算 Signature 并与 Token 中的 Signature 对比——匹配说明 Token 未被篡改。

随机 Token 生成

  • 设置长度：Token 长度 8-256 位——API Key 建议 32 位以上，Session ID 建议 64 位以上。
  • 字符集：勾选大写（A-Z）、小写（a-z）、数字（0-9）、符号（!@#$）——至少选择一种。
  • 格式选择：原始格式（纯随机字符串）、UUID 格式（8-4-4-4-12）、Hex 格式（仅十六进制字符）。
  • 批量生成：设置生成数量——一次生成多个 Token，适合批量创建测试数据。
  • 点击生成：Token 立即生成并显示。
  • 复制结果：点击"复制"按钮复制单个 Token，或"复制全部"复制所有 Token。

JWT 生成

  • 设置 Secret：输入签名密钥——建议至少 32 字符的随机字符串。
  • 选择算法：HS256（最常用）、HS384、HS512——安全级别递增。
  • 填写声明：iss（签发者）、sub（用户 ID）、aud（受众）、exp（过期时间，分钟数）。
  • 时间声明：iat（签发时间）自动设为当前时间，exp 按设定的分钟数计算。
  • 自定义声明：添加自定义 JSON 键值对——如 role: "admin"、name: "John"。
  • 点击生成：完整的 JWT 立即生成——可直接用于 API 测试。

五、JWT 技术背景

  • 三段结构：Header（算法声明）+ Payload（数据声明）+ Signature（签名验证）。三段用 Base64URL 编码后用点号连接。
  • Header：JSON 对象，声明签名算法和 Token 类型——如 {"alg":"HS256","typ":"JWT"}。
  • Payload：JSON 对象，包含声明（claims）——注册声明（iss/sub/exp 等）和自定义声明。注意 Payload 不是加密的——任何人都能解码读取。
  • Signature：用 Secret 对 Header + Payload 签名——HMAC-SHA256(Header.Payload, Secret)。任何篡改都会导致签名验证失败。
  • 标准声明：iss（issuer 签发者）、sub（subject 主题）、aud（audience 受众）、exp（expiration 过期时间）、nbf（not before 生效时间）、iat（issued at 签发时间）、jti（JWT ID 唯一标识）。

注意事项

安全警告

  • Secret 保护：JWT 的 Secret 一旦泄露，攻击者可以伪造任意 Token——Secret 必须存储在环境变量中，不能硬编码。
  • Payload 非加密：JWT 的 Payload 只是 Base64 编码——任何人都能解码读取。不要在 Payload 中放置敏感信息（如密码）。
  • 过期时间：始终设置 exp 声明——没有过期时间的 JWT 一旦泄露就永久有效。建议 Access Token 15 分钟，Refresh Token 7 天。

JWT 注意

  • HS256 vs RS256：HS256 使用对称密钥（同一个 Secret 签名和验证），RS256 使用非对称密钥（私钥签名，公钥验证）——微服务间通信用 RS256 更安全。
  • Token 大小：JWT 随每个 HTTP 请求发送——Payload 越大，网络开销越高。保持 Payload 精简，只包含必要声明。
  • 存储位置：JWT 存储在 localStorage 易受 XSS 攻击，存储在 Cookie 需设置 HttpOnly 和 Secure 标志。
  • 刷新策略：Access Token 短期有效（15 分钟），Refresh Token 长期有效（7 天）——过期后用 Refresh Token 获取新的 Access Token。
  • 签名验证：服务端必须验证 JWT 签名——不验证等于不设防。同时验证 exp、iss、aud 等声明。

Token 注意

  • 随机性：Token 的安全性取决于随机性——使用 crypto.getRandomValues()（浏览器原生安全随机数）而非 Math.random()。
  • 长度建议：API Key 至少 32 字符，Session ID 至少 64 字符，CSRF Token 至少 32 字符。
  • 字符集：包含大小写+数字+符号的 Token 熵最高——但某些场景（如 URL 参数）不支持符号字符。
  • 唯一性：随机 Token 不保证全局唯一——高并发场景需要数据库唯一约束兜底。UUID v4 碰撞概率极低（2⁻¹²²）。

JWT 生成注意

  • 测试用途：本工具生成的 JWT 仅用于开发和测试——生产环境的 JWT 应由后端服务使用安全存储的 Secret 签发。
  • Secret 安全：在公共设备上生成 JWT 后，请清空 Secret 输入框和浏览器历史记录。
  • 算法选择：HS256 适合大多数场景——如果安全要求极高，使用 HS512。
  • 时间设置：exp 设置为从当前时间起的分钟数——如 15 表示 15 分钟后过期。

常见问题

  • Q: JWT 能修改 Payload 吗？A: 修改 Payload 后签名会失效——除非你有 Secret。这就是 JWT 的防篡改机制。
  • Q: JWT 过期了怎么办？A: 使用 Refresh Token 获取新的 Access Token——不需要用户重新登录。
  • Q: 为什么签名验证失败？A: 检查 Secret 是否正确——Secret 区分大小写。也检查算法是否匹配（HS256 vs HS512）。
  • Q: JWT 和 Session 有什么区别？A: Session 存储在服务端（需要数据库），JWT 存储在客户端（无状态）。JWT 适合分布式系统和微服务。
  • Q: 生成的 Token 安全吗？A: 使用浏览器原生 crypto.getRandomValues() 生成——密码学安全随机数，不可预测。
