工具简介

本工具使用 AES-256-GCM 算法在浏览器本地对文件进行加密与解密。AES-256-GCM 是一种现代认证加密方案，它同时提供三项安全保证：机密性（未授权者无法读取内容）、完整性（任何篡改都会被检测到）和认证（确保解密方使用正确的密钥）。加密时，密码通过 PBKDF2（SHA-256，100,000 次迭代）和随机盐派生为 256 位密钥，并配合随机 IV/Nonce 进行加密。

加密后的文件采用自包含格式：magic + version + salt + iv + ciphertext + tag。解密时无需手动输入盐或 IV，只需原始密码即可还原文件。如果加密文件在传输或存储过程中被篡改，GCM 认证标签验证会失败，解密将立即终止，从而有效保护数据安全。

所有加解密操作完全在浏览器内存中完成，文件内容不会上传到服务器。处理完成后，文件数据会从浏览器内存中释放，适合处理身份证件、财务资料、医疗记录、商业合同、设计稿、源代码等高度敏感文件。

四步完成文件加密

第一步：设置强密码

密码是解密文件的唯一凭证。建议使用 16 位以上包含大小写字母、数字和特殊符号的强密码。密码越长、越随机，暴力破解的难度就越大。避免使用生日、手机号、常见单词等低熵密码。

第二步：选择文件

点击上传区域选择需要加密的文件，或直接拖拽文件到上传区域。文件内容仅在浏览器内存中读取，不会上传到服务器。支持加密任意类型文件，包括文档、图片、视频、压缩包等。

第三步：点击加密

工具会自动生成密码学安全随机盐和 IV，通过 PBKDF2 派生密钥并使用 AES-256-GCM 加密文件。处理完成后，浏览器会自动下载以 .enc 结尾的加密文件（如 document.pdf.enc）。

第四步：安全解密

需要恢复文件时，切换到解密模式，上传 .enc 文件并输入加密时使用的密码。密码正确且文件未被篡改即可下载原始文件。

典型应用场景

隐私文件保护：加密个人身份证件、财务资料、医疗记录等敏感文件，防止设备丢失、被盗或未经授权访问导致的数据泄露。

云端备份加密：在上传文件到网盘、NAS 或云存储前，先对文件进行加密。即使云端账号被盗或服务提供商被入侵，攻击者也无法读取加密内容。

文件安全传输：通过邮件、即时通讯或 U 盘发送机密文件时，先加密再传输，接收方通过单独渠道（如电话、密码管理器共享）获取密码。

企业数据归档：对重要合同、设计稿、源代码、财务报表等商业资料进行本地加密归档，满足数据安全和合规要求。

技术优势

AES-256-GCM PBKDF2 随机盐与 IV 认证加密 自包含格式 本地处理 无需安装

安全注意事项：

  • 密码是解密的唯一凭证，工具不保存密码，忘记密码将无法解密文件
  • 建议使用 16 位以上包含大小写字母、数字和符号的强密码
  • 请通过不同于文件传输渠道的安全方式发送密码（如电话、密码管理器）
  • 大文件会占用较多浏览器内存，建议单文件不超过几百 MB
  • 加密文件建议保留原始文件名信息，便于日后识别
  • 建议对重要文件同时保留未加密的本地备份，以防密码丢失
  • 所有加解密操作在浏览器本地完成，文件不上传服务器

常见问题

问：密码忘记怎么办？

答：本工具不保存密码，也无法通过任何方式重置或找回密码。忘记密码将导致文件永久无法解密，请务必妥善保管密码。建议将密码记录在可靠的密码管理器中。

问：加密后的文件扩展名是什么？

答：工具会在原文件名后追加 .enc，例如 document.pdf 加密后保存为 document.pdf.enc。解密时会自动去除 .enc 并还原原始文件名。

问：可以加密多大的文件？

答：文件大小受浏览器可用内存限制。建议单文件不超过几百 MB；超大文件请使用专业桌面加密软件。处理完成后关闭标签页可释放内存。

问：解密失败怎么办？

答：请确认密码正确，且选择的是本工具生成的 .enc 文件。文件损坏、被篡改或使用不同工具加密都会导致解密失败。如果密码多次错误，请检查大小写和输入法状态。

问：AES-256-GCM 安全吗？

答：AES-256-GCM 是目前广泛认可的认证加密方案，被 TLS 1.3、IPsec、SSH 等主流安全协议采用。在正确实现和强密码保护下，目前被认为是安全的。本工具使用浏览器原生 Web Crypto API 实现，与系统级加密库安全级别相当。

安全最佳实践

  • 密钥保密：不要在代码仓库、前端配置或不安全渠道中泄露密钥或敏感凭证。
  • 本地优先：本工具所有计算在浏览器本地完成，处理完成后及时关闭页面，避免敏感信息驻留。
  • 结合多层防护：单一工具不足以构建完整安全体系，建议配合 TLS、访问控制、审计日志等措施。
  • 定期轮换：对长期使用的密钥、令牌或凭证建立轮换机制，降低泄露后的影响范围。
  • 选择合适算法：根据安全需求选择算法长度和模式，优先使用经过广泛验证的标准方案。

实战案例：接口请求安全加固

某团队在开放 API 时，需要为第三方调用者提供一种轻量且可靠的鉴权方式。通过 文件加解密工具，服务端为每个开发者分配唯一凭证，并要求请求中附带基于该工具生成的签名或令牌。

实施流程：

  1. 开发者在控制台获取由 文件加解密工具 生成的密钥或凭证。
  2. 调用 API 前，按照约定格式拼接请求参数与时间戳，使用 文件加解密工具 计算签名。
  3. 将签名放入请求头，服务端使用相同逻辑重新计算并比对。
  4. 若签名一致且时间戳在有效窗口内，则放行请求；否则拒绝，防止重放和篡改。

效果：该方案无需复杂证书基础设施，仅通过浏览器本地即可完成计算，部署成本低且兼容性好。
