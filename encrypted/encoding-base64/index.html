Base64 编码

Base64 编码：将任意数据变为"可打印文本"的通用语言

一、为什么需要 Base64 编码

  • 电子邮件协议（SMTP）最初只支持 ASCII 字符传输——图片、PDF、音频等二进制数据无法直接通过邮件发送。Base64 编码将任意字节序列转换为 A-Z、a-z、0-9、+、/ 这 64 个可打印字符——使二进制数据能在只支持文本的通道中安全传输。
  • 本工具支持文本和文件两种模式的 Base64 编解码。文本模式：输入任意文字，立即获得 Base64 编码结果，反之亦然。文件模式：上传图片/PDF/音频等，编码为 Base64 字符串（data URI 格式），也可将 Base64 字符串解码还原为原始文件。
  • 支持标准 Base64 和 URL-safe Base64 两种变体——标准变体使用 + 和 /，URL-safe 变体使用 - 和 _（避免在 URL 中产生歧义）。编码结果可直接用于 HTML img 标签的 src 属性、CSS background-image 或 JSON 数据字段。

二、Base64 编码原理

  • 编码规则：每 3 个字节（24 位）拆分为 4 个 6 位组，每组映射一个 Base64 字符。不足 3 字节时用 = 填充——1 字节余数补 2 个 =，2 字节余数补 1 个 =。因此 Base64 编码后的长度总是 4 的倍数。

三、核心功能

  • 文本编解码：输入任意文本，一键获得 UTF-8 编码的 Base64 结果。支持中文、emoji 等多字节字符——自动处理 UTF-8 编码。
  • 文件编解码：上传文件自动转为 Base64 data URI（如 data:image/png;base64,iVBOR...）。也可将 Base64 字符串解码还原为文件下载。
  • 双变体支持：标准 Base64（+/=）和 URL-safe Base64（-_=）一键切换——URL-safe 变体适合在 URL 参数和文件名中使用。
  • 纯前端处理：所有编解码在浏览器中完成——文件不上传到服务器，适合处理敏感数据。

五、Base64 基础知识

  • 编码原理：3 字节 → 4 字符。每 6 位二进制映射为一个 Base64 字符——64 = 2⁶，所以 6 位恰好能表示所有字符。
  • 字符集：A-Z（26）+ a-z（26）+ 0-9（10）+ /+（2）= 64 个字符。= 是填充符，不属于数据字符。
  • 体积膨胀：Base64 编码后体积增加约 33%——3 字节变为 4 字符。这是用空间换兼容性的代价。
  • 典型应用：邮件附件（MIME）、CSS 内联图片（data URI）、JWT Token 的头部和载荷、HTTP Basic Auth 的凭证编码。

注意事项

格式注意

  • 填充字符 =：Base64 长度必须是 4 的倍数——不足时用 = 填充。解码时工具自动处理填充。
  • 换行符：某些 Base64 实现每 76 字符插入换行符（PEM 格式）——本工具输出连续字符串，不含换行。
  • URL-safe 变体：将 + 替换为 -，/ 替换为 _，去掉 = 填充——适合在 URL 参数中使用。

体积说明

  • 编码膨胀：Base64 编码后体积增加约 33%——1MB 文件编码后约 1.33MB。
  • 大文件建议：超过 10MB 的文件不建议用 Base64 内联——体积膨胀会显著增加传输时间。
  • 图片优化：小图标（< 10KB）适合 Base64 内联减少 HTTP 请求；大图片应使用独立文件。

数据安全

  • 非加密：Base64 是编码而非加密——任何人都能解码。不要用于保护敏感信息。
  • 纯前端处理：所有编解码在浏览器中完成——文件数据不上传到服务器。
  • 公共设备：在公共设备上处理敏感文件后，请清空输入和剪贴板。

常见问题

  • Q: Base64 能加密吗？A: 不能。Base64 只是编码——目的是让二进制数据变为可打印文本，不提供任何安全性。需要加密请使用 AES/RSA。
  • Q: 编码后中文乱码？A: 确保使用 UTF-8 编码。如果原始文本是 GBK 编码，需要先转为 UTF-8 再编码。
  • Q: 解码报错？A: 检查 Base64 字符串是否完整——缺少字符或包含非法字符会导致解码失败。URL-safe 变体和标准变体不能混用。
  • Q: data URI 怎么用？A: 直接放入 img 标签的 src 属性——。也可用于 CSS background-image。
