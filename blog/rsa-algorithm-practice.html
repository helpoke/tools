加密安全

RSA 加密算法原理与实践：从数学基础到安全应用

📅 2026-08-24 ⏱️ 阅读时长：16分钟

引言：非对称加密的革命

1976 年之前，所有加密系统都是"对称的"——加密和解密使用同一把密钥。这意味着通信双方必须先安全地交换密钥——但在互联网上，这几乎不可能。

1977 年，Ron Rivest、Adi Shamir 和 Leonard Adleman 提出了 RSA 算法——第一个实用的非对称加密方案。它使用一对密钥：公钥加密、私钥解密。公钥可以公开给任何人，私钥只有持有者知道——彻底解决了密钥分发问题。

一、数学基础：RSA 依赖的三大数论定理

1.1 大数分解难题

RSA 的安全性建立在"大整数分解困难"之上——将两个大素数相乘很容易，但从乘积反推因数极其困难：

正向（容易）：p × q = n
  6329 × 7481 = 47,345,749  ← 瞬间完成

反向（困难）：n → p, q
  47,345,749 = ? × ?  ← 需要大量计算

实际 RSA 使用的密钥长度（2048 位）：
  n 是一个约 617 位的十进制数
  目前已知最快的分解算法（GNFS）需要：
  约 2^112 次运算 → 即使用全球所有计算机也需要数百万年

1.2 欧拉函数

欧拉函数 φ(n) 表示小于 n 且与 n 互素的正整数个数。对于两个素数的乘积：

若 n = p × q（p, q 为素数）：
  φ(n) = (p-1) × (q-1)

示例：n = 77 = 7 × 11
  φ(77) = 6 × 10 = 60
  （1 到 76 中，与 77 互素的数有 60 个）

欧拉定理：若 gcd(a, n) = 1，则 a^φ(n) ≡ 1 (mod n)
  → a^φ(n)+1 ≡ a (mod n)
  → 这是 RSA 加解密正确性的数学保证

1.3 模逆元

模逆元是 RSA 密钥生成的关键——找到 e 的模逆元 d，使得 e × d ≡ 1 (mod φ(n))：

示例：e = 7, φ(n) = 60
  求 d 使得 7d ≡ 1 (mod 60)
  
  使用扩展欧几里得算法：
  60 = 8 × 7 + 4
  7 = 1 × 4 + 3
  4 = 1 × 3 + 1
  
  反向代入：
  1 = 4 - 3 = 4 - (7-4) = 2×4 - 7 = 2×(60-8×7) - 7
  1 = 2×60 - 17×7
  
  所以 d = -17 ≡ 43 (mod 60)
  验证：7 × 43 = 301 = 5 × 60 + 1 ≡ 1 (mod 60) ✓

二、RSA 密钥生成与加解密全流程

2.1 密钥生成

步骤 1：选择两个大素数 p 和 q
  p = 61, q = 53（实际应用中为 1024 位以上的素数）

步骤 2：计算 n = p × q
  n = 61 × 53 = 3233

步骤 3：计算欧拉函数 φ(n)
  φ(3233) = 60 × 52 = 3120

步骤 4：选择公钥指数 e（1 < e < φ(n)，且 gcd(e, φ(n)) = 1）
  e = 17（常用值：3, 17, 65537）
  65537 = 2^16 + 1（费马素数，二进制只有两个1，加密效率高）

步骤 5：计算私钥指数 d（e × d ≡ 1 mod φ(n)）
  d = 2753（17 × 2753 = 46801 = 15 × 3120 + 1）

密钥对：
  公钥 (n, e) = (3233, 17)  → 公开给所有人
  私钥 (n, d) = (3233, 2753) → 自己秘密保存

2.2 加密与解密

加密（公钥操作）：
  明文 m = 65（字母 'A' 的 ASCII 码）
  密文 c = m^e mod n = 65^17 mod 3233 = 2790

解密（私钥操作）：
  密文 c = 2790
  明文 m = c^d mod n = 2790^2753 mod 3233 = 65 ✓

数学保证（欧拉定理）：
  c^d mod n = (m^e)^d mod n = m^(e×d) mod n
  因为 e×d ≡ 1 (mod φ(n))，所以 e×d = k×φ(n) + 1
  m^(k×φ(n)+1) mod n = m × (m^φ(n))^k mod n = m × 1^k mod n = m

三、RSA 的实际应用场景

3.1 HTTPS/TLS 握手

当你在浏览器访问一个 HTTPS 网站时，RSA（或 ECDHE）用于 TLS 握手阶段交换对称密钥：

TLS 握手简化流程（RSA 密钥交换）：
  1. 客户端 → 服务器：支持的加密算法列表
  2. 服务器 → 客户端：数字证书（包含 RSA 公钥）
  3. 客户端验证证书（CA 签名是否有效、域名是否匹配）
  4. 客户端生成随机"预主密钥"
  5. 客户端用服务器公钥加密预主密钥 → 发送给服务器
  6. 服务器用私钥解密得到预主密钥
  7. 双方根据预主密钥 + 握手随机数 → 生成会话对称密钥
  8. 后续通信使用对称密钥加密（AES）

为什么不全用 RSA 加密数据？
  RSA 加密速度比 AES 慢 100-1000 倍
  实际方案：RSA 交换密钥 + AES 加密数据（混合加密）

3.2 数字签名

数字签名是 RSA 的另一大应用——用私钥"签名"，公钥"验签"，证明消息确实来自发送者：

签名过程：
  1. 发送方计算消息的哈希值：H = Hash(消息)
  2. 发送方用私钥加密哈希值：S = Sign(H, 私钥)
  3. 发送方发送（消息 + 签名 S）

验签过程：
  1. 接收方用发送方公钥解密签名：H' = Verify(S, 公钥)
  2. 接收方计算消息的哈希值：H = Hash(消息)
  3. 比较 H' 和 H：
     相同 → 签名有效（消息未被篡改，确实来自发送方）
     不同 → 签名无效（消息被篡改或来源不可信）

安全保证：
  ✓ 完整性：消息被修改后哈希值变化，签名验证失败
  ✓ 身份认证：只有持有私钥的人才能生成有效签名
  ✓ 不可否认：发送方无法否认自己签过名

3.3 JWT Token 签名

JSON Web Token 使用 RS256 算法（RSA + SHA-256）进行签名：

JWT 结构：Header.Payload.Signature

Header：{"alg": "RS256", "typ": "JWT"}
Payload：{"sub": "1234567890", "name": "John", "exp": 1787620800}

签名过程：
  1. 将 Header 和 Payload 分别 Base64Url 编码
  2. 拼接：signingInput = base64Url(header) + "." + base64Url(payload)
  3. 计算 SHA-256 哈希：hash = SHA256(signingInput)
  4. 用 RSA 私钥签名：signature = RSASSA-PKCS1-v1_5(hash, privateKey)
  5. 最终 JWT = signingInput + "." + base64Url(signature)

验签过程（服务端）：
  1. 拆分 JWT 为三部分
  2. 用公钥验证 signature 是否匹配 SHA256(header + "." + payload)
  3. 验证 exp 是否过期

四、RSA 的安全威胁与最佳实践

4.1 已知攻击方式

  • 大数分解：量子计算机的 Shor 算法理论上可高效分解大整数，但目前量子计算机位数不足以威胁 2048 位 RSA
  • 侧信道攻击：通过测量解密时的功耗、时间等信息推测私钥——防御方法：恒定时间实现
  • 填充攻击：不安全的填充方案（如 PKCS#1 v1.5）可能被 Bleichenbacher 攻击——应使用 OAEP 填充
  • 小指数攻击：e=3 时若消息较短，可能直接开立方根还原明文——应使用 e=65537

4.2 密钥长度选择

安全等级对照：
  RSA 1024 位 ≈ 80 位对称安全 → 已被认为不安全（2013 年起不推荐）
  RSA 2048 位 ≈ 112 位对称安全 → 当前最低推荐标准
  RSA 3072 位 ≈ 128 位对称安全 → 推荐用于新系统
  RSA 4096 位 ≈ 140 位对称安全 → 高安全需求场景

性能参考（2048 位密钥）：
  密钥生成：约 100-500ms
  加密操作：约 0.5-1ms
  解密操作：约 10-20ms（比加密慢，因为 d 比 e 大）
  签名操作：约 10-20ms
  验签操作：约 0.5-1ms

五、痛点深挖：RSA 使用中的高频安全错误

RSA 本身是安全的，但"错误地使用 RSA"几乎总是致命的。以下是安全审计中最常发现的几类问题，每一类都曾造成真实的数据泄露：

  • 密钥长度不足：512 位密钥在 1999 年被攻破，768 位在 2009 年被攻破。2026 年的底线是 2048 位，涉及长期数据保护建议直接上 4096 位。小于 1024 位的密钥在现代计算力下可在数天内被分解。
  • 错误使用 PKCS#1 v1.5 填充：v1.5 填充存在 Bleichenbacher 预言机攻击——攻击者不断向解密方发送篡改密文，根据"填充是否合法"的响应差异逐步还原明文。Web Crypto API 默认的 RSA-OAEP 才是安全选择，它用随机数填充，无此风险。
  • 直接用私钥加密、公钥解密："签名"和"加密"在数学上都是模幂运算，但语义完全不同。用私钥"加密"的产物可以被任何人用公钥解出，且没有完整性校验——这不是加密，是裸签名。混淆两者会导致机密数据被公开。
  • 忽略 RSA 的长度限制：RSA 一次只能加密"密钥长度 - 填充开销"字节的数据：2048 位 + OAEP 只能加密约 190 字节。把大文件直接 RSA 加密必然报错。正确做法是混合加密：用 AES 加密内容，再用 RSA 加密 AES 密钥。
  • 小指数攻击与共模攻击：公钥指数 e=3 且密文较短时，可直接开三次方根破解；同一明文用同一模数发给两个不同指数的人，可被共模攻击还原。指数固定用 65537（0x10001），它是费马数，仅有 2 个 1 位，计算快且安全。
  • 不验证公钥来源：把 RSA 公钥写死在客户端代码里、或通过不安全的渠道分发，中间人可以替换公钥做 MITM。公钥分发必须走证书链（HTTPS）或指纹比对（SSH known_hosts）。

最危险的认知："我用了 RSA，所以数据安全了"。实际上加密链路中任何一个环节（随机数质量、密钥管理、填充方案、长度选择）出错，RSA 都救不了你。安全是系统属性，不是算法属性。

六、深入原理：CRT 优化与 PKCS#1 填充方案演进

RSA 的数学原理看似简单——模幂运算而已。但生产环境中的 RSA 实现涉及大量工程优化和安全填充方案，理解这些才能做出正确的技术决策。

6.1 中国剩余定理（CRT）优化：解密速度 4× 提升

标准 RSA 解密需要计算 m = c^d mod n，其中 n 是 2048 位大数，d 也是 2048 位。直接计算非常慢。CRT 优化将一次大模幂拆分为两次小模幂：

标准 RSA 解密：
  m = c^d mod n    （2048 位模幂，很慢）

CRT 优化解密：
  已知私钥中包含 p, q（n 的两个因子）
  
  步骤1：计算 dp = d mod (p-1), dq = d mod (q-1)
  步骤2：计算 m1 = c^dp mod p    （1024 位模幂）
  步骤3：计算 m2 = c^dq mod q    （1024 位模幂）
  步骤4：用 CRT 合并：
    qInv = q^(-1) mod p
    h = qInv × (m1 - m2) mod p
    m = m2 + h × q

  结果与标准解密完全相同，但速度提升约 4 倍
  原因：(n/2)² 的运算量约为 n² 的 1/4

实际影响：
  2048 位 RSA 解密：
    标准方式：~15-20ms
    CRT 优化：~4-5ms
  
  这就是为什么 TLS 握手能控制在几十毫秒内
  OpenSSL、Java、Go 的 RSA 实现默认都用 CRT

6.2 填充方案演进：从 PKCS#1 v1.5 到 OAEP

裸 RSA（直接对明文做模幂）是不安全的——同样的明文总是产生同样的密文，且容易被数学攻击。填充方案通过在加密前添加随机填充来解决这些问题：

PKCS#1 v1.5 填充（1993年，已被认为不安全）：
  格式：0x00 | 0x02 | 随机非零字节(≥8个) | 0x00 | 明文
  
  问题：Bleichenbacher 攻击（1998年）
  攻击者向解密服务器发送篡改的密文
  根据“填充是否合法”的响应差异（错误信息不同）
  逐步缩小明文范围，最终还原明文
  
  即使响应时间差异只有几微秒，也足以被利用
  这就是“预言机攻击”（Padding Oracle Attack）

OAEP 填充（Optimal Asymmetric Encryption Padding，2001年）：
  格式：0x00 | 种子掩码后的数据 | 数据掩码后的种子
  
  核心改进：
  • 使用两个不同的哈希函数（MGF1）
  • 填充包含完全随机数
  • 即使解密失败，也不泄露任何信息
  
  安全证明：在随机预言机模型下可证明安全
  
  实际选择：
  ✓ 新系统永远用 RSA-OAEP（SHA-256）
  ✗ 不要在新项目中使用 PKCS#1 v1.5
  △ 兼容旧系统时，必须实现恒定时间响应（不泄露填充状态）

七、技术选型决策：RSA vs ECC vs Ed25519

非对称加密不止 RSA 一种。现代系统中，ECC（椭圆曲线密码）和 Ed25519 正在快速取代 RSA。选型错误会导致性能瓶颈或安全风险：

非对称加密算法对比：
┌──────────────┬──────────┬──────────┬──────────┬──────────────┐
│   维度       │ RSA      │ ECDSA    │ Ed25519  │   推荐场景   │
├──────────────┼──────────┼──────────┼──────────┼──────────────┤
│ 密钥长度     │ 2048-4096│ 256-384  │ 256      │              │
│ (同等安全)   │          │          │          │              │
├──────────────┼──────────┼──────────┼──────────┼──────────────┤
│ 签名速度     │ △ 慢     │ ✓ 快     │ ✓✓ 最快  │              │
├──────────────┼──────────┼──────────┼──────────┼──────────────┤
│ 验签速度     │ ✓ 快     │ △ 较慢   │ ✓ 快     │              │
├──────────────┼──────────┼──────────┼──────────┼──────────────┤
│ 密钥/签名大小│ 大       │ 中       │ 小       │              │
├──────────────┼──────────┼──────────┼──────────┼──────────────┤
│ 量子安全     │ ✗ 威胁   │ ✗ 威胁   │ ✗ 威胁   │ 均不安全     │
├──────────────┼──────────┼──────────┼──────────┼──────────────┤
│ 实现难度     │ 中       │ 高       │ 低       │              │
├──────────────┼──────────┼──────────┼──────────┼──────────────┤
│ 行业标准     │ HTTPS/   │ TLS1.3/  │ SSH/     │              │
│              │ JWT/SSH  │ 区块链   │ 现代SSH  │              │
└──────────────┴──────────┴──────────┴──────────┴──────────────┘

同等安全级别下的密钥长度对比：
  RSA 2048 ≈ ECDSA 256 ≈ Ed25519 256（128 位安全强度）
  RSA 3072 ≈ ECDSA 384（192 位安全强度）

选型决策树：
  你的场景是什么？
  ├── 传统 HTTPS / JWT 签名 → RSA-2048（兼容性最好）
  ├── TLS 1.3 / 区块链 / 移动设备 → ECDSA (P-256)
  │   └── 密钥更小、速度更快、带宽更省
  ├── SSH / 现代协议 / 新系统 → Ed25519
  │   └── 签名最快、实现最简单、无随机数依赖
  └── 长期数据保护（>10年） → 考虑后量子密码（PQC）
      └── NIST 已标准化：ML-DSA (Dilithium)、ML-KEM (Kyber)

关键原则：
  ✓ 新系统优先考虑 Ed25519 或 ECDSA（性能优势明显）
  ✓ 需要广泛兼容旧系统时仍用 RSA-2048+
  ✗ 不要用 RSA-1024 或更短（已不安全）
  ✗ 不要用 ECDSA + 重复随机数（会泄露私钥！PS3 被黑事件）
  ✓ Ed25519 是确定性的，不依赖随机数质量，更安全

结语

RSA 算法的优雅之处在于它将纯数学（数论、欧拉定理、模逆元）转化为实用的安全工具。大数分解难题保证了"正向容易、逆向困难"，非对称密钥对解决了密钥分发困境。 虽然量子计算的发展可能在未来威胁 RSA 的安全性，但在当下，RSA 仍然是互联网安全的基石之一——从 HTTPS 到数字签名，从 JWT 到 SSH，无处不在。
