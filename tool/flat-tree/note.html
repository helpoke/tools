为什么要做扁平与树的互转？

后台系统里的菜单、部门、商品分类、评论回复都是层级不定的数据。数据库不方便把整棵树存成一段 JSON——改一个子节点要重写整列，也没法用 SQL 查某个节点的父链。通行的做法是平铺存放：每行记自己的 id 和父级 parentId，根节点写 0 或 null。查询时一句 SELECT * FROM sys_menu 全量拿回，前端再装配成 children 嵌套结构，交给树形控件、级联选择器、递归组件渲染。

这段"最后一步"看着只有十几行代码，坑却全在脏数据上：一条父记录被删掉，它下面整棵子树就凭空消失；两个人各自新增时撞了同一个 parentId，形成 A 是 B 的父、B 又是 A 的父；递归沿父链找根会直接栈溢出。手写实现往往写成 list.filter(...) 的两层循环，两万条数据要跑几十秒。

本工具把这段逻辑做成独立页面：一遍哈希索引建树（O(n)）、父链上色断环、孤儿与重复 ID 逐条列原因，同时支持反方向的树 → 扁平。粘进去就能看到结果和结构问题清单，不用为验证一段建树代码专门起个工程。

建树与断环是怎么做的？

核心是三步。第一步把所有记录（含已经嵌套的子节点）深度优先拍平成一份线性列表，第二步按 ID 建哈希索引并沿父链回溯上色，第三步把每个节点挂到父级的 children 数组里。

① 索引：id → 节点，O(n) 一次遍历 ② 判父链：沿 parentId 上溯，white 未访问 / gray 在当前链上 / black 已定性 遇到 gray ⇒ 成环 ⇒ 该节点父指针作废、提升为根，记录完整路径 遇到不存在 ⇒ 标记孤儿 ③ 挂接：parent.children.push(node)，保持原始顺序 示例数据里的 11(parentId=12) 与 12(parentId=11)： 从 11 出发 → 12 → 11，11 已在当前链上（gray） ⇒ 报告「检测到父子环 11 → 12 → 11，已断开节点 11 的父指向」 ⇒ 结果里 11 成为根节点，12 挂在 11 下面，两个节点都没有丢

统计子孙数量、深度、拍平也都使用显式栈的迭代写法，因此上千层的畸形数据不会触发 Maximum call stack size exceeded。只有在树已经确定无环之后，输出装配才使用递归，深度是数据本身的层级。

输入与输出

输入：左侧文本框接受四种格式——标准 JSON 数组、包在响应对象里的数组（会优先在 data / list / rows / items / records 等字段里找）、JSONL / NDJSON（一行一个对象）、以及已经嵌套好的树。也支持上传 .json / .jsonl / .ndjson / .txt / .log 文件（≤10MB），按 UTF-8 读取并自动跳过文件开头的 BOM。

输出：右侧是转换后的 JSON 文本，可直接复制或下载。下载文件名会带上方向标记，如 tree-2026-10-03.json、上传过文件则是 menu-table-tree-2026-10-03.json。输出框下方是结构问题清单，逐条写明问题类型、涉及的 ID 与处理办法；数据完全干净时显示「未发现结构问题」。非 ASCII 文件名会被替换成下划线，以免浏览器下载时乱码。

输入（后端菜单表原样导出）： [ {"id":1,"parentId":0,"name":"系统管理","sort":2}, {"id":2,"parentId":1,"name":"用户管理","sort":1}, {"id":9,"parentId":88,"name":"数据看板","sort":3} ] 输出（扁平 → 树，保留父级字段）： [ { "id": 1, "parentId": 0, "name": "系统管理", "sort": 2, "children": [ { "id": 2, "parentId": 1, "name": "用户管理", "sort": 1 } ] }, { "id": 9, "parentId": 88, "name": "数据看板", "sort": 3 } ] 结构问题清单： 节点 9 的父级 88 不存在（含 0 个子孙），已提升为根 统计条：节点 3 · 根节点 2 · 最大层级 2 · 结构问题 1

快速开始

  • 点载入示例：一份刻意埋了孤儿、父子环、自指和重复 ID 的后台菜单表会立刻建成树，先看问题清单怎么读。
  • 把接口返回或数据库导出的 JSON 整段粘进左侧，字段名不一致时改上面三个输入框。
  • 需要给树形控件用就关掉「输出中保留父级字段」，需要落库或二次校验就留着。
  • 反向操作把方向切成树 → 扁平，嵌套 JSON 会展开成带父指针的列表。

典型使用场景

  • 前端接菜单树：后端只给平铺的 sys_menu 列表，粘贴一次拿到 children 结构，直接塞进 el-tree / Ant Design Tree 的 treeData，省掉一段本地转换代码和一次联调。
  • 排查"菜单不见了"：某条菜单在页面上消失，用本工具跑一遍原表，问题清单会当场指出它是孤儿（父级被删）还是被重复 ID 覆盖。
  • 部门 / 区域 / 分类数据治理：导入组织架构或行政区划批量表之前先建树，环、自指、缺失上级在导入前就暴露，而不是导入后出现死循环。
  • 造测试数据：把嵌套的假数据拍平成带 parentId 的列表写入 SQL，或反过来把建表脚本导出的平铺数据组装成前端 mock。
  • 代码评审对照：同事提交的建树函数不确定对不对时，用同一份数据在这里跑一遍比对结果。
  • 评论区楼层还原：只有 replyToId 的评论列表，把父级字段改成这个名称即可组装成回复楼层。

工具优势

一遍索引 O(n) 建树 父链上色断环 孤儿含子孙计数 重复 ID / 自指定位到行号 双向转换 字段名完全自定义 兼容接口响应体 / JSONL 迭代遍历不栈溢出 最小化输出可直接引用 全程本地不上传

和"复制一段网上找的递归函数"相比，差别集中在异常数据上：常见写法遇到环会死循环、遇到孤儿静默丢弃、遇到 ID 类型不一致就整棵树塌成一个一个的根，而且都不告诉您发生了什么。这里把这三类问题变成可读的清单，并且明确说明每条是怎么被处理的——数据丢了不要紧，丢了却不知道才要紧。

注意事项

  • 问题清单不是可选装饰。输出结果里包含被工具"修好"的数据：断掉的环、提升的孤儿、忽略的重复 ID。请把这些行当成待清理的数据缺陷，回到源头修正后再转换，否则线上递归渲染仍会踩坑。
  • 根节点判定依赖约定。null、0、"0"、空串视为顶级；如果您的约定是 -1 或其他哨兵值，这类记录会按孤儿处理，结果位置一致但会多一条提示。
  • 数字 ID 精度问题属于输入而不是本工具。JS 的安全整数上限是 253-1，雪花 ID 这类 19 位长整数在 JSON.parse 阶段就可能已经末几位失真，导致两个不同节点被判成重复 ID。若您的 ID 是雪花算法生成，请在导出时保持字符串形式。
  • 关闭「孤儿提升为根」时结果会少数据。孤儿子树被排除，只在清单里留一行说明（含子孙数量）。想确认有没有被排除，看清单里有没有「未列入结果」字样。
  • 不做业务字段处理。工具只增删父级字段和子级数组，不会替您过滤 status=0 的停用菜单、按权限裁剪节点或重命名 key；这些请在转换前后自行完成。
  • 容量与性能：单次最多 50000 个节点，超出部分忽略并提示；文件不超过 10MB。转换本身是线性的，页面延迟主要来自把很长的结果文本写入文本框，数据量大时可选「最小化」输出或直接下载。
  • 非法 JSON 不做猜测性修复。尾逗号、单引号、注释这类 JSON5 写法不会被强行解析，而是原样给出解析器的报错与位置，避免"修复"过程悄悄改变数据含义。如需格式化，可先用 JSON 格式化工具排查。
