什么是 CSV 编码转换？

CSV 编码转换是一款专门处理"文件能打开、中文全是乱码"这类问题的在线工具。系统、数据库、ERP 导出的 CSV 常用 GBK/GB18030 保存，而浏览器、Git 仓库、现代后端普遍使用 UTF-8；台湾与港澳的合作方则常见 Big5。同一个字节流被按错误的字符集解读，就会出现 æ±‰å­—、娑堟伅、ä½ å¥½ 这类面目全非的文字。

工具的思路很直接：把文件的原始字节读进浏览器，用 TextDecoder 按正确的字符集重新解码，再按您指定的目标编码重新写出字节并下载。整个过程是纯粹的 字节级转码——不解析 CSV、不改分隔符、不动行列、不裁剪空格，除了您主动选择的换行符统一之外，正文逐字符原样保留，避免"转一次码多出几列"的二次破坏。

为了让转完的文件真的能被下游接受，输出侧专门保留了 UTF-8 + BOM 这一档：Excel 2016 及更早版本双击无 BOM 的 UTF-8 文件时仍会按系统 ANSI 码页解析而显示乱码，加上 BOM 之后即可双击直开；同时提供无 BOM 的 UTF-8 给程序读取，也提供 GBK（ANSI）与 Big5 用于回写给只认老码表的前置机与批量代付模板。

乱码是怎么产生的？

字符集（码表）定义"哪个数字对应哪个字"，编码定义"这个数字怎么变成字节"。汉字在 UTF-8 里是 3 个字节 E6 B1 89，在 GBK 里是 2 个字节 BA BA。用错表去读，字节就被翻译成完全不同的字符：

原始内容：汉字 UTF-8 字节： E6 B1 89 E5 AD 97 按 UTF-8 读 → 汉字 ✔ 按 GBK 读 → 姹夊瓧 ✘（GBK 把 E6B1 / 89E5 / AD97 拼成三对） 原始内容：汉字 GBK 字节： BA BA D7 D6 按 GBK 读 → 汉字 ✔ 按 UTF-8 读 → ���� ✘（不是合法的 UTF-8 序列，浏览器逐字节给出替换符 U+FFFD）

所以"修乱码"的本质不是改文字，而是找回原始字节再用正确的码表重读一遍。这也是为什么工具强烈建议直接上传文件，而不是把已经乱码的文字复制粘贴进来——粘贴的那一刻，错误的解码结果已经被固化成 Unicode 文本，原字节信息就丢了。

支持的输入与输出

输入文件：.csv、.tsv、.txt、.log，单文件建议不超过 50MB；也可直接把文本粘贴进输入框。

读取（解码）编码：自动识别、UTF-8、GBK、GB18030、Big5、EUC-KR、Shift_JIS、Windows-1252、UTF-16LE、UTF-16BE。

写出（下载）编码：UTF-8 + BOM、UTF-8（无 BOM）、GBK（ANSI 中文）、Big5（繁体中文）、UTF-16LE + BOM。

换行符：保持原样 / 统一 CRLF（Windows、Excel、老系统）/ 统一 LF（Linux、macOS、容器）。

如何快速开始？

第一步：载入文件

点击"上传 CSV/TXT"选择乱码文件，或点"载入示例（GBK 文件）"先体验一次完整流程。文件会以自动识别出的编码解码后显示在左侧，统计条同时给出字节数、编码、行列数与替换符数量。

第二步：确认没有乱码

盯着左侧预览里的中文看：如果仍是乱码，把"源编码"手动改成 GBK / GB18030 / Big5，页面会立刻用新编码重新解码原始字节；"替换符"计数为 0 且文字读得通，说明编码找对了。

第三步：转码并下载

选择"输出编码"（给 Excel 就选 UTF-8 + BOM）与换行符，点击"转码"查看输出统计，再点"下载"保存文件。文件名会自动追加编码后缀，例如 orders-utf8-bom.csv；也可以直接"复制"结果文本。

典型应用场景

财务对账：ERP 导出的 GBK 报表在 Excel 里是一团乱码，转成 UTF-8 + BOM 后双击即读，再去"CSV 数据转换"里做去重与排序。

银行 / 社保批量代付：网银前置机只认 ANSI(GBK) 文本，把 UTF-8 模板转回 GBK 再上传，避免整批文件被打回。

两岸资料交换：台湾合作方发来的 Big5 客户名单，本地转成 UTF-8 后交给 CRM 导入，姓名不再是一串问号。

开发与运维：老项目遗留的 GBK 测试数据批量转成无 BOM 的 UTF-8，防止前端解析时第一个字段名带上 ï»¿ 前缀，也避免 Git 差异里出现整文件变更。

数据入库接力：统一成 UTF-8 之后，接"表格转 SQL INSERT"生成导入语句，或接"Json/CSV 转图表"出汇报图，链路里不会再有第二个人被乱码卡住。

注意事项：

  • "源编码"只作用于文件原始字节；粘贴进来的文本已是 Unicode，改"源编码"不会有效果。
  • 自动识别只采样前 256KB 字节，若文件开头一大段都是英文、中文集中在后部，可能判成 UTF-8，请手动指定。
  • GBK 与 Big5 常能互相解出"看着像字"的结果，最终对不对要靠人眼看预览语义，工具不做语义判断。
  • 输出 GBK/Big5 时，映射表里没有的字符（emoji、生僻字、简繁另一侧的字）会写成 ? 并计入"无法映射"；不为 0 时建议改出 UTF-8。
  • 工具不会解析或重排 CSV，若您怀疑源文件本身列错位，请用"CSV 数据转换"检查，而不是在这里反复转码。
  • 大文件全部驻留浏览器内存，超过 50MB 请拆分处理；公共设备建议使用无痕模式，关闭页面即清除数据。

常见问题

问：编码自动识别会不会认错？

答：有可能。识别顺序是 BOM 优先 → 纯 ASCII → UTF-8 严格校验 → 对 GBK/Big5/EUC-KR/Shift_JIS/Windows-1252 逐个解码并统计解出的中日韩文字数量，取分值最高者。难点在于同一串字节在 GBK 与 Big5 下都可能合法解出文字，程序无法判断语义。所以一定要看左侧预览，读不通就直接切"源编码"，每次切换都会用新码表重新解码原始字节。

问：输出 GBK / Big5 时为什么有些字符变成了 ?？

答：GBK、Big5 的字符集比 Unicode 小得多：GBK 不含 emoji 与 CJK 扩展区生僻字，Big5 只收繁体字，用它写简体内容会有大量字无处映射。工具按行业惯例写入 ?（与 Excel「另存为 ANSI」的行为一致），并在输出统计里报告"无法映射"的数量，方便您决定是否改出 UTF-8。

问：UTF-8 到底要不要加 BOM？

答：看下游。给人用 Excel（含 2016 及更早版本）、WPS 双击打开，选 UTF-8 + BOM；给程序读（pandas、MySQL LOAD DATA、前端 CSV 解析）、进 Git 仓库、Linux/macOS 工具链处理，选 无 BOM 的 UTF-8，否则 BOM 会被当成正文，导致首个列名变成 ï»¿姓名 这类取值失败问题。不确定时：先按"谁来读"想一遍，别按"谁来写"。

问：为什么下载不支持 GB18030 / EUC-KR / Shift_JIS？

答：浏览器只提供这些遗留编码的解码器（TextDecoder），没有编码器。本工具的 GBK / Big5 输出是靠原生解码器枚举全部合法双字节组合、在本地反查出「字符 → 字节对」映射表实现的，只对这两种最常用的中文码表开放写出；GB18030 的四字节区（生僻字）未被枚举，因此也不作为输出选项。读取方向则完整支持。

问：我的文件会被上传吗？

答：不会。文件用 FileReader.readAsArrayBuffer 读成字节数组后就在内存里，解码、编码、生成下载都发生在浏览器本地，页面不发送任何携带文件内容的请求，可用 F12 的 Network 面板验证。

问：粘贴进来的乱码能直接修好吗？

答：不能，也不该。粘贴的瞬间，错误的解码结果已经固化成 Unicode 文本，原字节信息丢失，再解一次只会越改越乱。正确做法是把原始文件上传进来重新解码。如果手头只有已经乱码的文本，可以让对方重发原文件。

问：支持 Safari / 手机浏览器吗？

答：需要浏览器支持带遗留编码的 TextDecoder：Chrome/Edge 38+、Firefox 63+、Safari 14.1+ 均可。若某个码表不被支持，工具不会静默出错，而是提示"当前浏览器不支持该编码"，此时改用 UTF-8 输出或在桌面浏览器上处理。手机端可用，但大文件建议用电脑，内存更充裕。

使用最佳实践

  • 先验证再批量：拿一份文件转成 UTF-8 + BOM 后用 Excel 打开确认语义正确，再处理同类文件，避免整批返工。
  • 盯两个计数：源统计里的"替换符"不为 0 说明码表选错；输出统计里的"无法映射"不为 0 说明目标编码装不下，二者都为零才是干净的一转。
  • 记住下游是谁：人读 → UTF-8 + BOM；机器读 → UTF-8 无 BOM；老系统 → GBK。这一条判断比任何自动识别都可靠。
  • 留好原始文件：转码文件用于交付，原始字节文件用于复查；一旦怀疑转错，重新上传原文件即可复原。
  • 与其他工具接力：编码统一后再进"CSV 数据转换"做去重排序、进"数据脱敏"打码手机号与身份证、进"表格转 SQL INSERT"生成入库语句，避免每一步都被乱码绊一次。
